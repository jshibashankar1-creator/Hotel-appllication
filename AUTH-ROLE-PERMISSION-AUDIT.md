# HotelHub Authentication and Role/Permission Audit

**Date:** 2026-09-27  
**Scope:** 16 configured accounts; deployed API; local web dashboard using that API; Expo customer app in web preview and Android Expo Go.  
**Result:** **FAIL — critical authentication, authorization, payment-flow, and tenant-isolation defects.**

## Test safety and evidence

- All 16 configured identities were authenticated against the real API. Credentials were read from the project's supplied test-credential documentation; no passwords or bearer tokens are included here.
- The deployed API returned HTTP 200 for health and real hotel/search requests. New bookings, payment orders, refunds, room/property changes, support-ticket mutations, and room CRUD were **not** submitted: the configured backend is not identified as a test environment, the project backend defaults to production payment mode, no test payment credentials were available in the local environment, and the API exposes existing customer and financial data.
- Login updates the account's `lastLoginAt` on the server. No booking, payment, refund, room, or hotel business data was intentionally changed. One foreign-hotel `PUT` used an empty JSON body to test authorization; it returned 200 but made no field changes.
- Logout endpoint behavior was checked with a Super Admin token; the same stateless-token behavior applies across account roles, but the logout UI was not cycled separately for all 16 users.
- The web dashboard was run locally against the deployed API. The Super Admin dashboard rendered live API-backed counts and totals. Other role dashboards were checked through their API endpoints, not all visually navigated.
- The customer app was exercised in Expo web and bundled/launched in Expo Go on the available Android emulator. Search and review were inspected; no payment was submitted.
- A direct MongoDB read was not performed. Source inspection shows API routes use the JSON-file store rather than MongoDB models, so the requested API-to-MongoDB persistence chain could not be verified.

## Detailed failures

| # | Severity | Screen / API | HTTP status and observed error | Probable root cause | Recommended fix |

| 1 | Critical | Web login; `POST /api/auth/login` | Login screen ships with a prefilled administrator identity and password. The API also has fixed role-wide password fallbacks. No error is returned for those fallback credentials. | Development/demo credentials are embedded in the login view and accepted by the production login controller independently of the stored password hash. | Remove all default credentials and password fallbacks; rotate all affected accounts; require unique hashed credentials and rate limiting; invalidate existing sessions. |
| 2 | Critical | `GET /api/hotels/admin`, `GET /api/bookings/admin` | **200** for all 4 owners and all 4 hotel admins; each response included records from other properties (4 hotels and 18 bookings were present in the tested dataset). No denial message. | The role guard accepts hotel operators for platform-wide list routes; returned collections are not tenant-filtered. | Restrict these endpoints to explicitly authorized platform roles, or filter every result by the authenticated user's assigned hotel. |
| 3 | Critical | `PUT /api/hotels/:id` | **200** for `hoteladminA` against a foreign hotel using an empty body; no field was changed. ## Other tested outcomes

- **Authentication:** all 16 configured accounts returned HTTP 200 and the expected role. Wrong password and unknown email returned 401; empty credentials returned 400; malformed email was rejected with 401. Missing and invalid bearer tokens returned 401. Expired-token behavior was not exercised against the deployed signing key.
- **Customer booking isolation:** all 4 `GET /api/bookings/my` responses were scoped to the authenticated customer; no foreign `customer_id` was present.
- **Owner-specific reads:** all 4 owners and all 4 hotel admins received HTTP 200 for assigned-property dashboard, property, rooms, bookings, earnings, and profile endpoints. Bookings/revenue were scoped in those endpoints. Three hotel-admin identities shared one assigned property; one was assigned another property.
- **Hotel editing:** an owner’s no-op update to a foreign hotel returned 403; a hotel-admin’s no-op update to a foreign hotel returned 200. Foreign-room no-op updates returned 403 for the owner and tested hotel admin.
- **Platform modules:** Super Admin APIs for dashboard, users, customers, hotels, bookings, payments, refunds, KYC, support, reports, settings, and audit logs returned 200. General Admin dashboard returned 200 and `/admin/users` returned 403. Support and Finance dashboards/KPI and their configured primary modules returned 200; unauthorized Finance data routes are listed above.
- **Web availability:** the configured API root returned 404 (`Route GET / not found.`); there is no web dashboard served from that root. The local Vite dashboard did render the Super Admin view using live API responses. UI navigation of every dashboard role/module was not completed.
- **Payment and mutation paths:** no new booking/payment/refund, KYC change, support ticket, room, or hotel was created or modified. Thus booking IDs, payment status, confirmation, My Bookings after purchase, CRUD success, refund processing, and payment-to-database consistency remain **BLOCKED**, not PASS.

5. **Tenant-isolation failures:** 22 observed checks — 16 cross-tenant list responses from hotel routes, 4 additional cross-tenant hotel/booking list responses from admin routes, 1 global KYC list exposed to a hotel admin, and 1 foreign-hotel update authorized for a hotel admin
6. **Booking failures:** 0 booking attempts; 4 customer booking flows BLOCKED
7. **Payment failures:** 0 payment attempts; 4 customer payment flows BLOCKED
8. **API failures:** 1 broken logout endpoint (404); authorization violations returned success-shaped 200 responses
9. **UI failures:** 4 observed mobile issues (date offset, unavailable guest/room selection, missing pickup choices, inconsistent currency)
10. **Critical issues:** shared/fallback credentials; cross-tenant customer/property/booking exposure and hotel-admin foreign-hotel edit; unverified payment success path
11. **Recommended fixes:** remove demo auth bypasses; enforce per-route RBAC and tenant scoping; secure hotel mutations; complete gateway verification before booking; honor room counts; implement session revocation; use MongoDB-backed persistence; fix the mobile booking controls/date/currency defects.
